# Three.js Semantic Capability Taxonomy

## 1. Inventory Principles

The unit of migration is "the behavior semantics the source project relies on", not Three.js class
names or text matches. One source location may yield multiple capability items; the same capability
appearing in multiple locations is merged into one item, retaining all key evidence.

Each capability item must include:

```json
{
  "id": "material.pbr",
  "criticality": "visual_core",
  "confidence": "high",
  "evidence": [
    {
      "file": "src/scene.ts",
      "line": 42,
      "symbol": "MeshStandardMaterial",
      "reason": "The primary models use PBR materials"
    }
  ],
  "notes": "Metalness and roughness determine the subject's appearance"
}
```

`asset.*` capabilities must also include `asset_paths`, and every path must point to a file that
already exists in the input project. Files exported after running the program, baked offline, or newly
generated by the migration Agent cannot be added retroactively as source assets.

```json
{
  "id": "asset.gltf-glb",
  "asset_paths": ["public/models/robot.glb"]
}
```

`criticality` can only be:

- `visual_core`: removing it distorts the subject's appearance or spatial structure.
- `interaction_core`: removing it makes the main user flows unavailable.
- `runtime`: affects runtime behavior, but can be rebuilt by a different mechanism.
- `infrastructure`: build, debugging, or performance infrastructure.

`confidence` can only be:

- `high`: call sites and data flow have been read, and the actual runtime semantics can be confirmed.
- `medium`: the call is confirmed, but criticality or the runtime branch still needs judgment.
- `low`: only text, dependency, or unresolved dynamic-call evidence exists.

A `low` confidence on a core capability blocks admission until manual source review is completed.

## 2. Content Ownership

The following capabilities inherently belong to the source program code and must continue to be owned
by Kotlin/ECS code after migration:

- `geometry.*`
- `animation.procedural`
- `effect.*`
- textures/visual content generated at runtime by Canvas, DataTexture, shaders, or algorithms

They may map to `MeshResource`, `MeshModel`, `MeshInstancesResource`, runtime materials,
Bitmap/TextureResource, Entity pools, or ECS Systems, but must not be exported as models, images,
animation assets, or Editor bundles and then loaded.

`material.*` capabilities are the exception to the above rule: material semantics defined by shaders
may be reconstructed by ShaderGraph and recorded as `editor_authored`; all other procedural content
still retains code ownership.

`asset.*` only means external files the input project already owned before migration. Models, textures,
audio, and video that originally existed in the source project may be retained, or given one-to-one
format conversion when the format is incompatible. Format conversion must not change content
ownership, nor become an entry point for assetizing procedural content.

## 3. Stable Capability Identifiers

### Project and Modules

| ID | Typical Signal | Semantics |
|---|---|---|
| `project.native-three` | `from "three"`, `require("three")` | Direct use of Three.js |
| `project.typescript` | `tsconfig.json`, `.ts` | TypeScript source |
| `project.dynamic-import` | `import()`, runtime module paths | Dynamic loading of code or capabilities |

React Three Fiber, Threlte, TresJS, Babylon.js, and similar are not capability items but
source-framework rejection conditions.

### Scene Graph

| ID | Typical Signal | Semantics |
|---|---|---|
| `scene.hierarchy` | `Scene`, `Group`, `add/remove` | Parent-child hierarchy and visibility |
| `scene.transform` | `position`, `quaternion`, `scale`, matrices | Spatial transform |
| `scene.layers` | `layers.set/enable/mask` | Layered visibility or per-Pass separation |

### Geometry

| ID | Typical Signal | Semantics |
|---|---|---|
| `geometry.primitive` | Box/Sphere/Plane/Cylinder, etc. | Built-in base geometry |
| `geometry.buffer-static` | `BufferGeometry` + fixed attributes | Custom static mesh |
| `geometry.buffer-dynamic` | `needsUpdate`, DynamicDrawUsage | Runtime vertex updates |
| `geometry.instancing` | `InstancedMesh`, instance matrices | Batch instances of the same mesh |

### Assets

| ID | Typical Signal | Semantics |
|---|---|---|
| `asset.gltf-glb` | `GLTFLoader`, `.gltf/.glb` | glTF model |
| `asset.usd` | `.usd/.usda/.usdc/.usdz` | USD model |
| `asset.obj` | `OBJLoader`, `.obj` | OBJ model |
| `asset.fbx` | `FBXLoader`, `.fbx` | FBX model |
| `asset.hdr` | `HDRLoader/RGBELoader`, `.hdr` | HDR environment or texture |
| `asset.texture` | `TextureLoader`, `DataTexture`, texture URL | 2D/data textures |
| `asset.font` | `FontLoader`, font files | 3D or UI fonts |
| `asset.video` | `VideoTexture`, video elements | Video texture |

### Materials

| ID | Typical Signal | Semantics |
|---|---|---|
| `material.unlit` | `MeshBasicMaterial` | Unlit material |
| `material.lambert-phong` | Lambert/Phong/Toon | Traditional lit material |
| `material.pbr` | Standard/Physical | PBR material |
| `material.shader` | `ShaderMaterial`, GLSL strings | Custom shader |
| `material.raw-shader` | `RawShaderMaterial` | Fully custom pipeline shader |
| `material.node-tsl` | Nodes, TSL, `three/tsl` | Node/WebGPU material graph |

`onBeforeCompile` is classified into `material.shader` or `material.raw-shader` according to the actual
modification scope, and must not be classified by base material name alone.

|---|---|---|

### Viewpoints

| ID | Typical Signal | Semantics |
|---|---|---|
| `view.camera-framing` | single-camera position/target/fov/zoom, fit bounds | Subject framing direction, look-at target, and picture scale |
| `view.camera-presets` | named camera presets, viewpoint buttons, lerp transitions | User-selectable semantic observation positions |

Viewpoint capabilities describe what the user ultimately sees and do not require the target side to
own the system camera. The target can reconstruct the same observation result through scene-root
inverse transforms, a model wrapper, a view root, or fit/framing state. Only same-frame multiple
projections or multi-Pass compositing belong to `render.multi-camera`.

## 4. Criticality Determination

Criticality is determined by its role in the user experience, not by API type:

- When the main subject uses ShaderMaterial, `material.shader` is `visual_core`.
- When it is used only for an optional glow, it may be `runtime` and may be removed.
- When a Raycaster drives the main gameplay operations, it is `interaction_core`.
- When it is used only for desktop debug selection, it may be `infrastructure`.

Criticality must be determined only after reading the initialization paths, main loop, state machines,
and user entry points.

Web UI is not an ancillary item. The complete DOM/component tree, routing, state, event bindings, and
responsive rules must be inventoried downward from the page entry point; do not search only the code
surrounding Three.js imports.
