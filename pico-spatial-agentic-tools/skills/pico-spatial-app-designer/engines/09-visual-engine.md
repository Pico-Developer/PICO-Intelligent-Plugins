# Visual Grammar Synthesis Engine

## Responsibilities

Starting from domain semantics, environment, emotional goals, risk, and information density, generate a visual grammar specific to this project. Produce tokens and reject at least two alternative visual directions. Unless independently derived with a reason given, do not reuse any named visual concept from a case study.

Role: `visual_designer` / `spatial_design_system_designer`. Reasoning conclusions are recorded in [`roles/review-templates/visual-system-spec.md`](../roles/review-templates/visual-system-spec.md) (Section 3, Design Tokens; Section 7, Data Display and Semantic Contract).

## Inputs

- Domain model, research evidence, approved visual references
- Environment, emotional goals, risk, information density
- Reasoning conclusions from upstream stages

## Output (direct description, no longer bound to a Schema)

`visualSystem` is not "an explanation for designers to read", but the single source of truth for styling that downstream implementers consume verbatim. Every visual decision must be able to enter the component / data handoff spec, so it **must be expressed as structured data, not prose**. Writing prose like `"magenta + square border = critical"` cannot be stably consumed by engineering implementation, and the visual layer degrades into an unverifiable subjective description.

Directly describe the following canonical shapes in structured Markdown:

- **concept**: a named visual concept (independently derived, not reused from a case study).
- **typography.{role}**: `{family, size, line, weight}`. `family` takes `grotesk|sans|mono|serif`; implementers infer the five roles display/title/metric/body/caption in a domain-neutral way by descending `size` + the `mono` family, and **do not recognize specific key names**—domain-custom key names (such as `asset`/`decision`) can also be consumed. The hierarchy should cover enough roles to support real information density.
- **colorSemantics.{state}**: `{color(#hex), shape, label, desc, aliases[]}`. `color` is hexadecimal; `shape` takes `circle|square|triangle|dashed|diamond` (a **color-independent redundant encoding**, required for accessibility); `aliases[]` lists all aliases of that semantic in the data (including localized values, such as "Out of Stock"/"Pending Lock"), and the engine colors data values by matching on `state key` or `aliases` substrings. `label` is **the human-readable text of that semantic on the runtime UI** (such as "Critical"/"Degrading"/"Healthy baseline"): when a data value hits a semantic, the visible text is replaced by the `label`, and **not the machine enum in the data echoed back** (`high`/`falling`/`degrading`). `label` is required, written in wording end users can understand—it and `aliases` are a pair: `aliases` is for machine matching, `label` is for human reading. Semantic colors should cover the domain's key states.
- **materials.{name}**: `{desc, treatment(matte|glass|opaque), glassStyle(Thin|Regular|Thick|Thickest|none), opacity}`. The glass effect is a **system capability of the PICO spatial platform**, not a CSS effect: the PICO Spatial SDK provides a glass background material (*glass background material*) in four tiers `Thin / Regular / Thick / Thickest` (increasing degree of blurring the content behind), applied via `Modifier.backgroundMaterial(enable, style = Material.<tier>)`, and controlled at the WindowContainer level by `enableMaterialBackground` (`pico.spatial.windowcontainer.materialbackground`, enabled by default). Therefore, when `treatment=glass` you **must specify the `glassStyle` tier**, and the handoff implementer directly calls the system `Material.<tier>` rather than self-drawing a blur. `matte` → a solid card. The Web preview using `backdrop-filter: blur + semi-transparency` is only a **preview approximation of the four-tier system glass**, and must not be taken as the device's real material.
- **Spatial semantics and boundaries of glass tiers**: the thicker the tier (Thick/Thickest) = the blurrier the background and the stronger the foreground focus; the thinner (Thin) = the more visible the background and the closer to the environment layer—use the tier to express **depth hierarchy** rather than only piling up colors. **The glass background material is only available within a WindowContainer** (fact source: PICO "Glass Effect"); a 3D scene inside a Stage / Volumetric cannot rely on glass to guarantee readability and must use a solid backing or Vibrant instead. But under MR / passthrough, glass lets the real world show through, threatening text contrast: panels carrying key states, body text, or forms should choose a thicker tier or overlay a solid backing that guarantees contrast (echoing §4 Readability and PICO-COLOR "not by color alone"). Note the platform known issue—the glass effect of the SpatialUI side-bar Tab Bar may display abnormally, and a fallback must be declared where involved.
- **vibrantStyle**: SpatialUI's **dynamic color-mixing system capability** (*Vibrant Style*, fact source: PICO "Vibrant Style"), which adjusts element brightness in real time according to the background color and luminance, used to maintain readability and visual consistency on **complex / passthrough / high-dynamic backgrounds**. It is centrally switched at the app level by the meta-data `com.pico.spatial.ui.isVibrant` (enabled by default), and at the code level uses `Color.Vibrant` + `Modifier.vibrantEffect(level)`, with 9 tiers total (darkest→ultralight). **Limitations**: it only supports monochrome scenes (monochrome background / text), not images or gradients; when disabled it falls back to Android 2D rendering, and `Color.Vibrant` will display as black. Therefore, when a panel/text needs to be above a passthrough or complex background, prefer declaring the use of Vibrant to guarantee readability, rather than inventing a CSS blend; regions containing images/gradients cannot rely on Vibrant and must be given a separate solid backing.
- **depth hierarchy depth**: depth is Z-axis front-to-back layering (fact source: PICO "Depth and Layout")—**2D content is always at the back of the "box"**, and depth participates in Align/Padding/Scale. The visual hierarchy should be organized with the depth semantics of "near = important" rather than only stacking colors; Planar depth is locked at 640dp, and depth differences are used for the layered expression of foreground focus vs environmental backing.
- **materialsByState**: the material strategy must be consistent with the **space state**—under Full Space (exclusive, can be fully virtual), foreground panels can use a dark solid backing + glass-tier layering; under Shared Space / MR passthrough, the background is uncontrollable, and key panels must use a thicker glass tier, Vibrant, or a solid backing to guarantee contrast.
- **tokens**: `{accent, surface, brandPrimary, ...}` (hexadecimal), handed off as the primary color, surface color, and brand color.
- **environmentAdaptation**: the adaptation strategy under light/dark environments and passthrough / immersive backgrounds (contrast, brightness, readability).
- **scale**: a unified metric scale `{spacing[], radius[], iconSize[]}` (4/8dp basis); component metrics must reference the scale tiers, and it is prohibited for each component to write its own magic numbers. See visual-system-spec §3.4.
- **windowLayout.{window}**: **the window structure and in-window layout are a required visual deliverable, not an optional explanation**. Each major WindowContainer must give: the window shell (form / default logical size / min / max / content area contentInset / docked attachments referencing interaction §8, with sizes referencing the PICO methodology results of interaction §9, not self-invented), an in-window layout **structure diagram** (ASCII: solid boxes = window / region boundaries, dashed boxes = component placeholders), region → component mapping (no orphan regions, no unplaced components), inter-region spacing, and reflow. The visualization of the in-window 2D layout lands here; the spatial placement geometry (anchor/x/y/w/h/z, attachment docking) is authoritative in interaction spec §14, and the two must not contradict each other. See visual-system-spec §5.0.
- **componentMetrics.{component}**: each core component must give **internal metrics** (dp/sp): container corner radius, padding, internal element gap, stroke, icon iconSize, primary/secondary text (referencing typography roles), and minimum hit target hitTarget. Icons / spacing / corner radius reference `scale`, font sizes reference `typography`, and corner radius and hit target must fall within the PICO platform numeric specs of §8. Component metrics and `sizing` must be able to hold within the content area of the owning window's default / min / max; under Compact / Constrained you must not pass by scaling text or hit targets as a whole. Do not write prose like "icon is a bit large" or "leave some margin". See visual-system-spec §5 "Anatomy · Internal Metrics".
- **Component background is optional, and custom color and glass are mutually exclusive**: the background of an in-window component is **optional**—it may be unset (none, falling directly onto the parent container), or set to a custom color background (customColor, the color chosen by the component itself, not limited to a solid color) **or** a glass background material (`glassStyle`, four tiers), but **the same component must not stack a custom color + glass at the same time** (choose one); the glass background material is only available within a WindowContainer. The component declares the chosen scheme in the `background` metric item of componentMetrics.

## Closed-Loop Constraint of "Visual as Implementation Input"

- Implementers consume `typography`, `colorSemantics`, `materials`, `scale`, `windowLayout`, `componentMetrics`, and `tokens` to generate the font hierarchy, semantic colors, shape redundant encoding, window structure, component internal metrics, and state expression; newly added visual semantics must have a stable key, a structured value, and a human-readable `label`/`desc`, and cannot only write prose like "stronger glass feel" or "highlight high risk".
- **The "change the design → change the delivery spec" closed loop**: replacing the hex of some semantic color, the corresponding design fact and engineering handoff fields must change accordingly; changing the font family, the font-hierarchy handoff fields must change accordingly. Changing the design while the delivery spec stays the same is drift.
- **Remove review noise**: DESIGN THESIS / the design thesis, layer names · container names, component classification, skeleton region names, AUGMENT/SUBWINDOW labels, the component `purpose` explanation, etc. are metadata for designers / auditors to read, and should stay in the reasoning and review documents; they **must not be disguised as final App text**. Text facing the end user should only be content the real App will display (app name, status labels, component data).
- **sampleData is runtime-data fidelity**: fill purely display fields with human-readable text (`"Vibration Sensor Array"` rather than `"vibration_array"`); fields that both display and drive coloring may retain the machine enum for `aliases` matching, but **you must declare a `label` for the corresponding semantic in `colorSemantics`**, otherwise the enum may go straight into the final screen.

## Prohibitions

- replacing structured visual fields with prose;
- reusing a case study's named visual concept without independent derivation;
- describing project-level derivations as PICO official hard rules;
- letting information that implementation must consume appear only in the thesis, explanations, or review comments;
- letting a machine enum go straight into the final UI without `label` translation.
